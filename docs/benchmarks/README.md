# Benchmark — PL/SQL Lens review rules

Everything here is regenerated by `make bench` (no LLM, no network) and compared byte for byte; the only
step that costs money is `make bench-llm`, whose recorded outputs are committed. Results:
[results.md](results.md) · raw numbers: [raw/](raw/) · frozen data: [data/](data/).

## What is measured

Seven deterministic rules (PLL001–PLL007, contract in [../rules.md](../rules.md)) against **seeded defects**
with a known location, plus **hard negatives** (near-misses that must not fire).

### Ground truth
* **Templates** (`src/plsql_lens/bench/templates/<split>/PLLnnn[.hard].json`) were written by Sonnet subagents
  from `docs/rules.md` only — they were forbidden from reading the rule implementation, as in F2. Each split has
  per rule **10 defect variants and 10 hard-negative variants** (5+5 "base" in the style of the contract, 5+5
  "hard" syntactic corner cases: comments inside tokens, keywords inside strings and q-quotes, labels, nested
  blocks and local subprograms, `$IF`, CASE/IF/LOOP nesting). `dev` and `test` use **different template sets**
  (different authors-in-a-prompt, different styles: lower-case/2-space vs UPPER-CASE/4-space) and **different
  seeds** (dev 1001, test 2002). Format and rules for writers: [TEMPLATE_SPEC.md](TEMPLATE_SPEC.md).
* **Instances**: the generator (`plsql-lens bench`, `src/plsql_lens/bench/generate.py`) fills placeholders with
  seeded random names and literals and strips the `-- @expect` markers (so nobody who reads the files, including
  the LLM baseline, sees the answer). Per split: 50 defect instances and 50 hard-negative instances **per rule**
  (350 + 350). PLL007 defects have 3 or more occurrences each, so 165 expected spans.
* **Two kinds of items** per split: (a) 70 *standalone* synthetic packages of 5 snippets each; (b) 35 *injected*
  files — copies of real utPLSQL package bodies (disjoint base files per split, none from the F2 held-out
  reserve, ≤ 400 lines) with 10 snippets inserted before the closing `END` (derived files: NOTICE item 5).
* **Manifest**: every file, every snippet *region* (line span, rule, defect/negative, template id) and the exact
  expected lines. `data/<split>/manifest.json`; each file's SHA-256 is inside it.
* PLL007 counts repeats per unit, so incidental literals (`2`, `'unknown'`) shared by two snippets would create
  findings nobody labeled. The generator therefore gives every non-designed literal of a PLL007 template a
  value that occurs nowhere else (designed literals are the `@@num@@`/`@@str@@` placeholders; 0, 1, empty and
  single non-alphanumeric strings, ORA-20xxx codes and type sizes are kept).

### Matching (the definition of TP / FP / FN)
Findings are deduplicated by `(file, rule, line)`. For a finding of rule *R* at line *L* of file *F*:

1. If *L* lies in a generated region of rule *R*: **TP** when the region is a defect and *L* is one of its expected
   lines; otherwise **FP** (wrong line in a defect, or anything in a hard negative).
2. If *L* lies in a region of another rule: not scored ("cross-rule", counted and published).
3. If *L* is outside every region: **FP** in a standalone file (the boilerplate is clean); in an injected file it
   is real corpus code with unknown ground truth, so it is *background* — not scored, counted and published.

An **FN** is an expected line with no finding. Intervals are **95 % Wilson score intervals** for precision
(TP/(TP+FP)) and recall (TP/(TP+FN)); F1 = 2TP/(2TP+FP+FN) with the same interval applied to TP/(TP+(FP+FN)/2)
(an approximation). Counts are per expected span, not per item. Correct-but-harmless findings count as TP here;
usefulness is measured separately (below).

### Before / after
* **before** = `src/plsql_lens/` exactly as of `ca4ba438b3f0086a1a603b4726bbb45d346dd60f` (origin/main at the start of F4:
  F2 + F3, untouched), exported from git and run through the same script as "after".
* **after** = the current rules. Tuning (on `dev` plus the five false positives known from F2's real-corpus QC):
  PLL004 recognises aggregates nested in expressions (`NVL(MAX(x), 0) + 1`), `LISTAGG`, excludes analytic
  (`OVER`), scalar-subquery and `HAVING` cases; PLL006 does not treat an operand that is part of an arithmetic or
  `||` expression as a simple operand (`a - b < 3`); PLL007 treats `''''` (an escaped quote) as the single
  non-alphanumeric character it is — this last one was found by the actionable-rate labeling on the real corpus,
  after the dev tuning, and fixed before the single `test` run. `docs/rules.md` was updated accordingly.

### Real corpus, held-out reserve
The "after" rules are rerun on the 259 real corpus files used in F2 and compared with F2's counts, listing every
finding removed or added (results.md; no F2 finding was added). The five hand-labeled F2 reserve files
(`tests/heldout/`) are scored with the same definitions.

### Actionable rate
On top of TP/FP, a seeded sample (seed 4004, ≤ 15 findings per rule, real corpus, rules as of the sample) was
labeled for *would a maintainer change the code because of it*. Rubric: [actionable/RUBRIC.md](actionable/RUBRIC.md);
labels: [actionable/labels.json](actionable/labels.json). **The labels were produced by the working session
(a Sonnet subagent, spot-checked by the lead), not by the code's maintainers**, with the instruction to answer
"no" when in doubt.

### LLM-only baseline
40 files of `test` (20 standalone + 20 injected, chosen by seed 3003) were given to `claude-sonnet-5-5` through the
`claude-cli` backend with the lean flags from F3, with the rules contract of `docs/rules.md` and **no access to the
rule engine**; it answered a JSON list of `{rule, line}` which the same scorer scores, next to the rules on the same
files. Projected cost from a 4-file probe: 1.3–1.4 USD (cap 2 USD); actual in results.md. Prompts and raw
responses: [llm_baseline/responses.json](llm_baseline/responses.json) (`make bench` replays them without calling
the model; `make bench-llm` re-runs them and costs money).

## Reproduce
```bash
make bench       # regenerates data/, raw/, results.md; verifies the seals; no LLM
make bench-llm   # re-runs the LLM-only baseline (COSTS MONEY, capped at 2 USD)
```
`make bench` run twice produces byte-identical `docs/benchmarks/` (checked with `diff -r` during F4).
It needs the full git history (it exports the "before" rules with `git archive`).

## Threats to validity (read before quoting numbers)
* **Ceiling effect / circularity.** The templates were written by the same model family that built the rules and
  from the same contract; both versions of the rules, and the LLM, score ~1.0 on `test`. The benchmark shows the
  rules implement their contract on many syntactic variants; it does **not** show they find the defects people
  care about in the wild, and it cannot rank the LLM against the rules (both score ~perfectly).
* **Synthetic defects.** Snippets are short, clean-room code; real defects are messier. Variants are 10 per rule
  and split; instances differ only in names/literals.
* **`test` is not very discriminating for the tuning**: the tuned constructs (nested aggregates, arithmetic
  operands, `LISTAGG`) are in the dev templates but not in the frozen test templates, so before = after on `test`;
  the effect of tuning is visible on `dev` and on the real corpus, not on `test`.
* **Generator flaw found after the final run.** One `test` miss (PLL005, `injected/ut_suite_tag_filter_008.pkb`,
  line 405) is an artifact: its base file ends with an initialization block, and the generator inserted the
  snippets *inside* it (3 of 35 injected `test` files share that base). The data is frozen, so it stays counted
  as an FN here; excluding it the PLL005 recall would be 49/49. Fix for a future benchmark version, not applied.
* **Corpus size/diversity**: 10 base files per split, all from utPLSQL; injected files share a base. Real-corpus
  numbers come from 259 files of three projects.
* **LLM-labeled actionable sample**: small (≤ 15 per rule), strict rubric, one labeler; PLL001/003/005 have 6/1/0
  sampled findings, so their intervals are wide or undefined.
* **Templates were generated by LLM subagents** and then reviewed by the lead only for contract ambiguity; before
  sealing, three `test` template items were edited for contract ambiguity (PLL005 `WHILE c%FOUND` → plain `LOOP`
  with `FETCH`; PLL007 `1.0` and case-variant strings removed), using `docs/rules.md` wording only.
* **Looked at per-item failures?** On `dev`: yes, freely, during tuning. On `test`: the lead saw only the aggregate
  tables until the rules were final; afterwards the single FN was inspected to explain it (no rule change followed).
